# Experiment Agent One：多 Agent 群聊式视频工坊方案

> **方案定位：**
> 将视频工坊从节点画布式工作流，升级为以群聊为主要交互入口、以多 Agent
> 协作为执行方式、以确定性任务引擎和共享项目空间为基础的内容生产工作台。
>
> **当前决策：** 采用「人机协作」自主程度（模式
> B）与「混合面板」布局。本文是产品与技术方案草案，不代表已经完成实现或验证。

------------------------------------------------------------------------

## 1. 项目目标与核心判断

### 1.1 改造目标

用户通过自然语言与一个 AI
制作团队协作。用户提出视频制作目标、修改意见或具体问题；总导演 Agent
理解意图并组织专业 Agent
完成剧本、分镜、生图、配音、配乐、视频生成、合成与质检等工作。

用户不再需要手动搭建节点、配置连线或理解复杂的工作流拓扑，而是通过群聊了解进展、参与讨论、调整方向，并通过侧边面板查看和控制各
Agent 的实际工作状态。

### 1.2 核心产品形态

-   **中间：项目群聊。** 用户与总导演、专业 Agent 在同一会话空间中交流。
-   **左侧：Agent 列表。**
    展示团队成员、职责、在线状态、当前任务和未读消息。
-   **右侧：动态工作面板。** 根据当前选中的 Agent
    或任务，展示详细参数、进度、产物、日志和控制操作。
-   **后台：多 Agent 调度系统。**
    负责任务拆解、依赖管理、并发执行、状态持久化、资源调度和异常恢复。
-   **底层：共享项目空间。**
    统一管理剧本、分镜、台词、素材、时间轴、任务、缓存和最终产物。

### 1.3 关键原则

**群聊是交互方式，不是执行引擎。**

Agent
可以通过群聊公开讨论、提出建议和汇报结果，但实际任务必须由后台任务系统创建、调度和追踪。不能仅凭
Agent
在聊天中说"我开始生成了"就认定任务已经启动，也不能仅凭它说"完成了"就认定产物合格。

采用：

-   前台：自然、可理解、可参与的群聊体验。
-   中台：明确的 Agent 编排、任务状态机和事件路由。
-   后台：确定性的工具执行、数据管理、权限控制和质量检查。

## 2. 用户体验与界面布局

### 2.1 桌面主界面

目标比例为 16:9 桌面工作区，建议采用三栏布局：

  ----------------------------------------------------------------------------------------
  区域                    主要内容                    交互方式
  ----------------------- --------------------------- ------------------------------------
  左侧栏                  Agent                       选择 Agent、查看未读与任务
                          团队列表、状态、任务摘要    

  中央栏                  项目群聊、用户输入、Agent   发送消息、回复、引用、审批
                          消息、任务事件              

  右侧栏                  当前 Agent                  修改参数、查看产物、暂停/恢复/停止
                          或任务的详细控制台          
  ----------------------------------------------------------------------------------------

布局采用**混合面板**：

-   左侧 Agent 列表固定，保证团队结构始终可见。
-   中间群聊保持稳定，作为主要交互区域。
-   右侧面板根据当前选中的 Agent、任务或素材动态切换。
-   右侧面板可以折叠，给中央群聊留出空间。
-   三个区域分别滚动，避免整个页面一起滚动。
-   小屏幕或窗口较窄时，允许侧栏折叠，不强行维持三栏。

### 2.2 左侧 Agent 列表

每个 Agent 条目建议显示：

-   头像或专属图标。
-   名称与职责。
-   当前状态：空闲、思考中、执行中、等待输入、等待审批、失败、已完成、已暂停。
-   当前任务简述。
-   未读消息或待处理事项提示。

首期建议的 Agent：

1.  总导演 Agent（Supervisor）
2.  剧本 Agent
3.  分镜 Agent
4.  生图 Agent
5.  配音 Agent
6.  配乐 Agent
7.  视频生成 Agent
8.  后期合成 Agent
9.  质检 Agent

不要求首版全部独立上线。应根据现有工具能力逐步接入，避免为了凑齐角色而创建没有真实执行能力的
Agent。

### 2.3 中央群聊

群聊消息需要区分消息类型：

-   用户消息。
-   Agent 发言。
-   Agent 之间的公开讨论。
-   任务创建、开始、进度、完成和失败等系统事件。
-   需要用户决策的审批卡片。
-   产物预览与文件引用。

建议每条 Agent 消息展示：

-   Agent 名称。
-   消息时间。
-   消息正文。
-   关联任务（如有）。
-   消息类型或执行状态。
-   相关产物、日志或参数的跳转入口。

支持用户：

-   在公共群聊中发言。
-   @指定 Agent。
-   回复或引用某条消息。
-   对某项方案提出修改。
-   对高影响操作进行确认或拒绝。
-   查看 Agent 的讨论过程，但可以折叠低价值的内部过程，避免群聊刷屏。

### 2.4 右侧动态面板

选中不同对象时，右侧展示不同内容。

**选中 Agent：**

-   Agent 职责与能力说明。
-   当前任务和历史任务。
-   当前执行步骤。
-   任务进度与运行时间。
-   使用的模型、工具和资源。
-   暂停、恢复、停止等控制。
-   Agent 产物与错误记录。

**选中任务：**

-   任务目标与输入。
-   任务状态与依赖。
-   执行日志。
-   输入、输出文件。
-   重试、取消、重新执行。
-   上游和下游任务关系。

**选中素材：**

-   图片、音频、视频或文档预览。
-   所属镜头、台词或任务。
-   版本历史。
-   来源与生成参数。
-   替换、标记采用、回滚等操作。

### 2.5 资源监控

可以在右侧面板或独立抽屉中展示：

-   GPU 使用率、显存占用。
-   CPU、内存和磁盘空间。
-   本地模型与服务状态。
-   当前运行任务数、排队任务数。
-   API 调用量和成本（适用时）。
-   TTS、图片生成、视频生成、FFmpeg 等服务状态。

资源数据应来自真实监控接口，不能由 Agent 自行估算后作为真实数据展示。

## 3. Agent 团队与职责划分

### 3.1 总导演 Agent（Supervisor）

总导演是用户的主要沟通对象，负责组织工作，不直接包办所有专业执行。

职责：

-   理解用户目标、约束和验收标准。
-   将目标拆解为可执行任务。
-   选择需要参与的专业 Agent。
-   管理任务依赖与并行关系。
-   汇总专业 Agent 的意见。
-   识别冲突、缺失信息和风险。
-   在需要用户决策时发起询问。
-   汇总执行结果并组织验收。

总导演不能仅根据聊天文本判断任务完成，必须读取任务系统中的真实状态和产物检查结果。

### 3.2 专业 Agent

  Agent            主要职责                           典型产出
  ---------------- ---------------------------------- --------------------
  剧本 Agent       故事结构、文案、台词、节奏         剧本、台词清单
  分镜 Agent       镜头拆解、画面设计、时长规划       分镜表、镜头描述
  生图 Agent       根据视觉要求生成或处理图片         图片素材、生成参数
  配音 Agent       角色、音色、语速、情绪与台词配音   音频文件、配音映射
  配乐 Agent       音乐风格、节奏、时长与音轨处理     配乐、音轨配置
  视频生成 Agent   动态镜头、视频素材生成             视频片段
  后期合成 Agent   时间轴、字幕、混音、编码与封面     最终视频及工程文件
  质检 Agent       检查素材和最终成片                 QA 报告、问题清单

Agent 的职责应按能力和工具权限划分，而不是简单地让每个 UI
模块对应一个互不相干的程序。

一个专业领域未来可以有多个 Agent。例如配音导演负责音色策略，配音执行
Agent 负责生成，音频质检 Agent 负责检查；它们可以共用同一套 TTS 服务。

### 3.3 项目管理员（确定性服务）

项目管理员不必是一个大模型 Agent。建议作为普通程序服务实现，负责：

-   工程数据读写。
-   素材登记和路径管理。
-   任务状态持久化。
-   版本号与并发控制。
-   缓存索引。
-   产物与来源关系。
-   文件完整性检查。
-   操作审计。

Agent 可以提出修改请求，但项目数据必须通过受控接口提交，不能任意覆盖其他
Agent 的状态或项目文件。

## 4. Agent 协作模式

### 4.1 自主程度：模式 B------人机协作

本项目选择**人机协作模式**：

-   用户提出目标和约束。
-   Agent 可以主动讨论、提出建议、分配子任务。
-   总导演可以组织专业 Agent 并行工作。
-   专业 Agent 可以请求其他 Agent 提供信息或素材。
-   遇到重大决策、需求冲突、成本风险或不可逆操作时，向用户确认。
-   用户随时可以介入、修改方向、暂停或取消任务。

不采用完全自由、无边界的 Agent
群聊。所有任务都必须有明确的负责人、输入、输出、状态和终止条件。

### 4.2 公开讨论、私下执行、公开汇报

建议采用三段式协作：

1.  **公开讨论：** Agent 在群聊中提出方案、说明依赖和风险。
2.  **私下执行：** Agent
    调用工具完成任务，输出进度事件，不必把每个内部步骤都变成聊天消息。
3.  **公开汇报：** Agent 汇报结果、产物、问题和下一步建议。

用户可以看到重要过程，但不应被大量低价值的内部思考或重复状态消息淹没。

### 4.3 Agent 之间的沟通

Agent 之间可以：

-   请求信息。
-   请求素材。
-   提交修改建议。
-   报告依赖已满足。
-   报告任务失败或输入不足。
-   对方案提出异议。

所有沟通都应带有项目 ID、会话 ID、消息 ID，以及必要时的任务
ID。涉及实际执行的请求必须转化为任务系统中的正式任务或任务变更。

### 4.4 防止循环与无效讨论

必须设置：

-   单任务最大讨论轮数。
-   最大重试次数。
-   Agent 调用预算或成本上限。
-   任务超时时间。
-   重复任务检测。
-   明确的完成条件。
-   需要用户介入的升级机制。

Agent 不得无限讨论或无限重试。

## 5. 后台执行架构

建议采用 Chat-first Multi-Agent 架构：

``` text
桌面 UI
├── 左侧：Agent 列表
├── 中间：项目群聊
└── 右侧：动态控制面板
          │
          ▼
Conversation / Event Gateway
├── 用户消息接收
├── Agent 消息路由
├── 系统事件推送
└── 实时状态同步
          │
          ▼
Supervisor / Agent Orchestrator
├── 意图理解
├── 任务拆解
├── Agent 选择
├── 依赖管理
├── 审批与权限检查
└── 完成条件判断
          │
          ├──────────────┐
          ▼              ▼
Agent Runtime       Task Engine
├── 专业 Agent      ├── 任务队列
├── 模型调用        ├── 并行执行
├── 工具调用        ├── 依赖调度
└── 结果汇报        ├── 重试与取消
                    └── 状态持久化
          │              │
          └──────┬───────┘
                 ▼
          受控工具与项目服务
          ├── Tool Registry
          ├── Project Store
          ├── Asset Manager
          ├── Cache Manager
          ├── Resource Manager
          └── QA / Validation
```

### 5.1 Conversation / Event Gateway

统一接收和分发用户消息、Agent
消息和任务事件。聊天消息与任务事件应有不同类型，避免把系统状态伪装成普通聊天文本。

### 5.2 Supervisor / Agent Orchestrator

负责决定谁来做、先做什么、哪些任务可以并行，以及何时需要用户确认。

### 5.3 Agent Runtime

提供 Agent 的运行环境，包括：

-   系统提示与职责定义。
-   可用工具列表。
-   模型配置。
-   上下文构建。
-   调用限制。
-   输出结构校验。
-   超时与错误处理。

### 5.4 Task Engine

负责真正的任务生命周期：

``` text
pending
  → ready
  → running
  → succeeded

running
  → waiting_approval
  → ready

running
  → failed
  → retrying
  → running

pending / ready / running
  → cancelled
```

任务状态必须由任务引擎维护，不以 Agent 的自然语言描述为准。

### 5.5 Tool Registry

把现有能力封装成可注册、可授权、可追踪的工具，例如：

-   本地 TTS。
-   云端 TTS。
-   图片生成。
-   视频生成。
-   FFmpeg。
-   网页渲染。
-   PPT 渲染。
-   文件读写。
-   媒体探测。
-   素材预览。

工具接口应定义输入 Schema、输出
Schema、超时、资源需求、是否可并发、是否需要审批和错误类型。

### 5.6 Project Store

统一保存项目结构、素材索引、时间轴、任务状态、缓存元数据和版本记录。避免多个
Agent 各自维护一份互相冲突的项目快照。

## 6. 视频项目的数据模型

建议逐步从"Markdown
清单作为核心数据源"升级为"结构化数据作为核心，Markdown
作为编辑与交换格式"。

核心对象：

  对象         职责
  ------------ ------------------------
  Project      项目元数据、设置、版本
  Script       剧本、章节、文案
  Shot         分镜、画面描述、时长
  Dialogue     台词、角色、语气
  Asset        图片、音频、视频、文档
  Timeline     镜头与音轨的时间关系
  Task         执行任务、依赖、状态
  CacheEntry   缓存指纹与产物映射
  Render       合成配置、输出与结果
  QAReport     检查结果和问题清单

### 6.1 稳定 ID

每个项目、镜头、台词、素材、任务和产物都应有稳定 ID。

例如：

-   `project_id`
-   `shot_id`
-   `line_id`
-   `asset_id`
-   `task_id`
-   `render_id`

显示序号只用于排序和展示，不能作为唯一身份标识。

尤其不能只依靠 `line_index` 把台词、角色音频和分镜绑定起来。

### 6.2 产物来源与版本

每个产物应记录：

-   产物 ID。
-   所属项目。
-   生成它的任务。
-   输入素材 ID 与版本。
-   使用的模型、工具和参数。
-   创建时间。
-   文件路径与校验信息。
-   当前是否被项目采用。

这样可以追溯素材来源、复用缓存和回滚版本。

### 6.3 缓存失效

缓存应依据实际依赖生成指纹，而不是简单地按模块或文件名判断。

例如修改某句台词，只应使相关配音及其下游依赖失效，不应无条件重做所有图片、配乐和无关镜头。

## 7. 典型视频制作流程

以用户提出"制作一条 60 秒科普视频"为例：

1.  用户在群聊提出目标、主题、风格和限制。
2.  总导演确认必要信息并制定制作计划。
3.  剧本 Agent 生成文案和台词。
4.  分镜 Agent 根据剧本拆解镜头、时长和视觉要求。
5.  总导演检查剧本与分镜是否满足目标。
6.  生图 Agent 根据分镜生成静态素材。
7.  配音 Agent 根据角色和台词生成音频。
8.  配乐 Agent 制作或选择合适的音乐素材。
9.  视频生成 Agent 处理需要动态生成的镜头。
10. 后期合成 Agent 根据时间轴、素材和字幕进行合成。
11. 质检 Agent 检查最终文件。
12. 总导演汇总结果，向用户交付预览和 QA 报告。

### 7.1 并行执行

可以并行的任务示例：

-   图片生成与配音。
-   不同镜头的独立素材生成。
-   不同角色的配音（前提是资源与文件隔离正确）。
-   音频分析与素材元数据检查。

必须等待依赖的任务示例：

-   最终合成必须等待所需素材和时间轴准备完成。
-   质检必须在对应产物生成后执行。
-   依赖最终时长的音乐处理应在时间轴确定后完成，或采用可调整的中间方案。

并行策略必须由任务依赖和资源约束决定，不能只因为 Agent
数量多就全部同时运行。

------------------------------------------------------------------------

## 8. 任务状态、并发与资源管理

### 8.1 任务状态

每个任务应显示：

-   状态。
-   负责人 Agent。
-   输入与输出。
-   开始时间和运行时长。
-   当前步骤。
-   进度（仅在可可靠计算时显示）。
-   错误与重试信息。
-   取消或暂停能力。

### 8.2 并发控制

需要区分：

-   **逻辑并发：** 多个 Agent 可以同时规划和沟通。
-   **任务并发：** 多个任务可以同时进入执行状态。
-   **资源并发：** 实际能同时使用多少 GPU、显存、CPU、模型服务和外部
    API。

资源管理器应为任务声明资源需求，并根据设备状态和任务优先级分配执行许可。

### 8.3 文件与状态写入

必须避免多个任务用旧快照覆盖整个项目。

建议：

-   项目元数据与任务数据分离。
-   每个任务只提交自己拥有的字段和产物。
-   共享集合采用增量合并或事务提交。
-   使用 revision/version 做乐观并发检查。
-   文件写入采用临时文件加原子替换。
-   任务完成后由项目服务登记产物。
-   发生冲突时明确重试或提示，不静默覆盖。

### 8.4 暂停、恢复与取消

停止一个 Agent 的任务，不应默认停止其他 Agent 的任务或共享服务。

任务取消应有明确的取消令牌和清理策略。共享 TTS、模型服务或 GPU
进程不能因为单个任务停止就被无条件终止。

------------------------------------------------------------------------

## 9. 权限、安全与用户确认

建议为 Agent 和工具定义最小权限：

-   只读项目资料。
-   写入指定项目目录。
-   创建素材。
-   修改指定对象。
-   执行本地程序。
-   调用外部 API。
-   发布或上传内容。

高影响操作应要求用户确认，例如：

-   删除项目或大量素材。
-   覆盖已有产物。
-   大额 API 消耗。
-   执行不受信任的脚本。
-   向外部平台发布内容。
-   修改全局配置或系统级资源。

所有关键操作应记录操作主体、时间、输入、结果和关联任务。

------------------------------------------------------------------------

## 10. 质量检查与验收

Agent 汇报完成不代表产物合格。最终产物必须经过程序检查和必要的人工验收。

视频 QA 至少包括：

-   文件存在且大小合理。
-   FFprobe 能读取媒体信息。
-   视频和音频流可正常解码。
-   分辨率、帧率符合项目设置。
-   时长与时间轴基本一致。
-   音频轨道存在且时长合理。
-   字幕文件可解析，时间范围有效。
-   镜头引用的素材均存在。
-   不存在明显的空素材引用。
-   最终文件能够正常播放。

可进一步增加黑帧、静音、音画错位、字幕越界和异常音量检查。

QA 结果应生成结构化报告，包含检查项、通过/失败状态、证据和修复建议。

------------------------------------------------------------------------

## 11. 技术选型原则

可研究的多 Agent 编排方案包括：

-   **LangGraph：** 适合有状态、可循环、带检查点和条件分支的 Agent
    工作流。
-   **Microsoft Agent Framework：** 值得研究其 Group Chat、Agent
    协作与工作流编排能力。

选型原则：

1.  先评估现有 Python 后端能否承载，不为追逐框架而整体重写。
2.  先做最小可用原型，再决定是否引入完整框架。
3.  Agent 编排框架不能替代项目数据模型、任务状态机和资源管理器。
4.  工具接口应尽量与具体 Agent 框架解耦。
5.  关键业务状态应由自己的项目服务持久化，避免只存在于框架内存中。

------------------------------------------------------------------------

## 12. 分阶段实施路线

### 阶段 0：现有项目审计与稳定化

目标：保护已有能力，避免新架构建立在不稳定基础上。

工作：

-   对当前本地版本和 GitHub 版本做差异检查。
-   梳理视频工坊现有模块、接口、文件格式和调用链。
-   修复已确认的数据覆盖、编号冲突、媒体识别等问题。
-   补充并发、取消、异常恢复和项目重载测试。
-   明确现有工具服务的输入输出契约。

验收：

-   现有核心功能有可重复的回归测试。
-   多模块并发不会静默丢失工程数据。
-   任务停止不会误伤其他独立任务。
-   项目重启后可以恢复可恢复的任务状态。

### 阶段 1：群聊 UI 原型

目标：先验证交互，不急于引入复杂多 Agent。

工作：

-   实现 16:9 三栏主界面。
-   左侧 Agent 列表。
-   中间群聊消息流。
-   右侧混合动态面板。
-   支持用户消息、模拟 Agent 消息和任务事件。
-   支持选中 Agent、查看详情和任务状态。

验收：

-   布局稳定。
-   消息类型清晰。
-   面板切换自然。
-   UI 不依赖真实 Agent 才能运行。

### 阶段 2：最小多 Agent 协作

目标：实现一个可控、可追踪的 Agent 团队。

首批建议：

-   总导演 Agent。
-   剧本 Agent。
-   分镜 Agent。
-   配音 Agent。
-   生图 Agent。

工作：

-   Agent 注册与职责定义。
-   消息路由。
-   结构化任务创建。
-   任务状态事件推送。
-   总导演分配任务。
-   Agent 结果回传。
-   用户确认机制。

验收：

-   用户提出一个小型视频目标。
-   总导演能拆解任务并分配。
-   专业 Agent 能真实调用工具。
-   群聊状态与后台任务状态一致。
-   失败任务能被识别和汇报。

### 阶段 3：接入现有视频生产工具

目标：复用已有 TTS、生图、配乐、视频生成、网页/PPT 渲染和 FFmpeg 能力。

工作：

-   建立 Tool Registry。
-   为工具定义输入输出 Schema。
-   接入资源限制和超时。
-   统一素材登记。
-   建立任务与产物的关联。
-   实现并行任务和依赖调度。

验收：

-   至少跑通一个端到端视频生产流程。
-   中途失败可定位。
-   任务产物可以追溯。
-   修改局部输入不会导致无关模块全部重做。

### 阶段 4：完整后期与质量检查

目标：从"能生成"提升到"能交付"。

工作：

-   时间轴管理。
-   多角色音频映射。
-   字幕、混音和视频合成。
-   产物版本管理。
-   QA 报告。
-   失败重试与局部返工。

验收：

-   能从项目输入生成最终视频。
-   最终视频通过基础自动化检查。
-   用户可以要求修改单个镜头或台词并局部重做。

### 阶段 5：增强协作能力

目标：让 Agent 团队更加主动，但仍然可控。

工作：

-   Agent 之间主动请求与建议。
-   群聊与私聊。
-   讨论轮数和预算限制。
-   更完善的任务恢复。
-   资源调度优化。
-   Agent 质量评价和执行历史分析。

验收：

-   Agent 能发现依赖缺失并主动请求。
-   不会无限讨论或无限重试。
-   重大决策能正确交由用户确认。
-   长任务中断后能恢复或明确说明不可恢复原因。

------------------------------------------------------------------------

## 13. 测试策略

必须覆盖以下类别：

### 单元测试

-   Agent 消息结构校验。
-   任务状态迁移。
-   工具输入输出 Schema。
-   项目数据模型。
-   稳定 ID 与引用关系。
-   缓存指纹计算。

### 集成测试

-   Supervisor 分配任务。
-   Agent 调用真实或模拟工具。
-   任务事件同步到群聊。
-   产物登记到项目空间。
-   右侧面板读取真实任务状态。

### 并发测试

-   多 Agent 同时提交产物。
-   多模块同时更新项目。
-   相同任务重复提交。
-   单任务取消时其他任务继续运行。
-   共享模型服务的并发调用。
-   随机完成顺序下项目数据完整性。

### 故障恢复测试

-   Agent 进程异常退出。
-   工具超时。
-   网络或 API 失败。
-   磁盘空间不足。
-   应用关闭后重新启动。
-   任务执行过程中用户取消。
-   产物写入成功但状态提交失败。

### 端到端测试

从用户提出制作目标开始，经过剧本、分镜、素材生成、配音、配乐、合成和质检，最终生成可播放的视频，并检查所有关键产物和工程记录。

------------------------------------------------------------------------

## 14. 首版范围与暂缓事项

为了控制风险，首版不追求"所有 Agent 都能自由讨论、自由执行所有事情"。

首版重点：

-   群聊主界面。
-   固定 Agent 列表。
-   动态右侧面板。
-   总导演调度。
-   少量专业 Agent。
-   结构化任务状态。
-   现有工具接入。
-   基础并发和失败处理。
-   可追踪的产物。

暂缓：

-   无限制 Agent 自由群聊。
-   Agent 自动创建和修改其他 Agent。
-   复杂的可视化 DAG 编辑器。
-   完全自主发布到外部平台。
-   过早引入复杂的分布式任务系统。
-   为每个细小功能都创建独立 Agent。

------------------------------------------------------------------------

## 15. 项目成功标准

这次改造是否成功，不应以 Agent
数量、聊天消息数量或界面效果衡量，而应以实际生产能力衡量。

核心指标：

1.  用户能否用自然语言启动一个完整视频项目。
2.  总导演能否正确拆分任务并安排依赖。
3.  专业 Agent 能否稳定调用现有工具。
4.  多任务并发时项目数据是否完整。
5.  用户能否随时介入并修改方向。
6.  局部修改能否只触发必要的下游任务。
7.  失败能否被定位、恢复或清楚汇报。
8.  最终视频能否通过自动化质量检查。
9.  项目关闭重启后，工程状态和产物关系是否仍然可靠。

## 16. 最终决策摘要

  决策项             当前方案
  ------------------ ------------------------------------------------------
  视频工坊主要交互   群聊式工作台
  旧节点画布         不再作为主要用户交互方式
  自主程度           模式 B：人机协作
  页面布局           混合面板
  中央区域           项目群聊
  左侧区域           固定 Agent 列表
  右侧区域           动态 Agent / 任务 / 素材控制台
  核心协调者         总导演 Agent
  专业执行者         剧本、分镜、生图、配音、配乐、视频、合成、质检 Agent
  后台执行           确定性任务引擎
  数据管理           结构化项目数据与统一项目服务
  Agent 沟通         公开讨论、私下执行、公开汇报
  关键保障           权限、并发控制、状态持久化、异常恢复、QA
  实施策略           先审计稳定，再做 UI 原型，再逐步接入 Agent 和工具

**最终方向：让 Experiment Agent One
从"用户手动搭建工作流的工具"，转变为"用户与一支 AI
制作团队协作完成工作的工作台"。**

群聊负责让协作变得自然，Agent
负责专业工作，任务引擎负责执行秩序，项目空间负责数据一致性，质量检查负责最终交付。

这五部分共同构成新一代视频工坊的基础。
