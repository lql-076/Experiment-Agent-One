### A3. 06:14:23 → 06:15:10 的 47 秒花在哪

证据（`data\logs\telemetry\behavior_2026-11.log`、`data\logs\report.jsonl`、`data\logs\bgm.log`）：

- 服务端 06:14:23 就打印「出好了：1795040062997_28868.wav · 60 秒 · 用了 4.2 秒」，说明音频已经写完。
- 06:14:23–06:15:10 期间，后端 `/api/tasks` 有 1 ms、`/api/agent/caps` 有 10 ms、`/api/studio/state` 有 5 ms 的记录 —— **事件循环没有被整段卡死**；慢的是要等外部进程/系统的接口：`/api/bgm` 3~8 秒（每次都要等配乐服务 `/health`，超时 3 秒）、`/api/hw` 3 秒超时成片、`/api/state` 5~8 秒。
- 同一时间报告里还有「本地模型服务在线了 / 停了」和 126 秒的 model_server 启动记录；那台机器刚开机，WMI/磁盘都很慢。

代码里确实有同步阻塞的位置（本轮只报告、没改）：

| 位置 | 做了什么 |
|---|---|
| `app/bgm.py:291-292` | `await c.get(...)` 把整首 WAV 一次性读进内存（`a.content`，60 秒 10.5 MB、200 秒 35 MB），再判断长度 |
| `app/bgm.py:311` | `tmp.write_bytes(a.content)` 在事件循环里同步整文件写盘 |
| `app/bgm.py:314` | `mediainfo.probe(p)` 同步读文件头最多 4 MB（`app/mediainfo.py:10,226`） |
| `app/bgm.py:318-323` | 同步写 `.json` 元数据、同步 sqlite 读写 `bgm_hist` |
| `app/bgm.py:230-232` | 完成后同步写 `feed`（`app/feed.py:22-27` 直接 append 文件）和 telemetry |
| `app/main.py:69-75, 91, 416-417` | 硬件采样已经放进 `asyncio.to_thread`，但 `/api/hw` 每个请求都会再起一次 `hw.sample()`；开机时 WMI 一项就要 3~5 秒，请求一多就排队（这就是 3 秒/8 秒超时的来源） |
| `app/main.py:128-141` | `live_checks` 每 10/30 秒重查一遍自检，个别项会在 15 秒超时内一直占着 |
| `app/bgm_server.py:276-278` | 峰值归一是在配乐服务进程里做的，而且发生在 06:14:23 那条「出好了」日志之前，**不在那 47 秒里** |

**结论：** 47 秒不是某一个函数卡住 47 秒。配乐这边「下载整文件 → 同步写盘 → 读 4 MB 文件头 → 写 json → 写 sqlite」是一串同步小阻塞，单次是毫秒到亚秒级；那 47 秒主要是刚开机时本地模型服务在加载（126 秒）+ WMI/磁盘很慢，后端的轮询和界面请求一起被拖住了。后端到配乐服务的文件下载用的是异步 httpx（不是阻塞式 HTTP），峰值归一也不在后端；但整文件 `a.content` 会完整进内存、写盘和 probe 在事件循环里同步做。`bgm.py` 这几处同步 IO 值得下一轮挪到线程里（本轮按要求没改）。

## B. 配乐页播放卡死（Out of Memory）修复（`ui/js/bgm.js`）

改动：

1. 静态波形只画一次，缓存在离屏 canvas（`BGM.wv`）；只有换曲、尺寸/DPR 真的变了才重画。页面重建时从缓存位图直接贴，不再每帧给 canvas 赋 width/height。
2. 播放时每帧只挪一条绝对定位的播放位置线（`#bgHead`，`transform: translateX(...)`），不再重画 canvas；时间文字最多每 100 ms 更新一次。
3. `bgmPeaks` 改成手工解析 WAV：读取 `ArrayBuffer`，认 RIFF/WAVE 和 `fmt`，16-bit PCM 直接按 Int16 取 200 个峰值，算完丢掉 `ArrayBuffer`；不是 PCM16 才退回 `decodeAudioData`。
4. 点击波形跳转、播放/暂停仍然走原来的 `bgmPlay`（点击用 `closest('#bgWave')` + 比例算 currentTime），行为没改。
5. `bgmLeave` 和窗口 `beforeunload` 都取消 `requestAnimationFrame`、清掉 1.5 秒轮询，`audio.pause()` 并 `removeAttribute('src')` + `load()`；离开时 `BGM.playing = null`，下次进来会重新设 src。

**验证：** 真 WebView2 临时窗口（pywebview 6.2.1 + Edge WebView2）打开 `?tool=bgm`，选刚出的 90 秒那首，静音（volume=0）+ loop 连续播放 195 秒；只观察进程，不杀任何进程。窗口是 7 个新出现的 `msedgewebview2.exe` 进程（基线之外），采样从 23:00:58 到 23:04:18，每 5 秒一次（去掉开头 count=0 的两行）：

- 前 2 分钟主要是首次加载/缓冲 16 MB 的 WAV 和首次绘制，工作集从 412 MB 涨到约 500 MB；之后走平（最后 45 秒 503~506 MB），私有内存在 318~410 MB 之间随 GC 波动，没有单调上涨，也没有 Out of Memory。
- 播放中 60 秒点暂停 → `paused=true`；63 秒继续；95 秒跳到 50% → `currentTime=46.96/90`；150 秒跳到 20% → `19.96/90`；195 秒时仍在播放。
