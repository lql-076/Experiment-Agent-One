## 一句话

配乐页播放不再每帧重画 canvas、不再把整首解码成 float，连续播放 3 分钟内存稳定；时长入口先限 120 秒；200 秒长曲溢到共享显存、34 秒起有噪音的根因查清了。

## 关键结论

1. **200 秒那首**：0–30 秒近乎静音，34–40 秒出现宽带噪音（8 kHz 以上能量 45%~54%），43 秒还有一下；44 秒后回到音乐。文件在 `data\bgm\tasks\1795029648346_25084.wav`。
2. **生成测试**（固定原描述 + seed 20261119）：60 秒 4.2 秒 / 6.48 GB；120 秒 8.1 秒 / 11.23 GB（专用显存 14.3 GB，不溢出）；200 秒 36 秒 / **22.47 GB**，专用显存顶满 15.9 GB、**共享显存 13.5 GB**——溢出到系统内存，真机那晚因此用了 609 秒，也容易出杂音。
3. **47 秒延迟**：不是某个函数卡 47 秒。配乐保存路径有整文件进内存、同步写盘、读 4 MB 文件头、写 json/sqlite 等同步小阻塞（`app/bgm.py:291-323`）；但那段时间主要是刚开机本地模型加载 126 秒 + WMI/磁盘慢，`/api/tasks` 仍有 1 ms 的记录，说明事件循环没整段卡死。
4. **播放修复**：静态波形缓存在离屏 canvas；播放只挪播放位置线；WAV 手工取 200 个峰值（PCM16 才走，其他退回 decodeAudioData）；离开/关窗清 rAF、定时器和 Audio.src。90 秒那首在真 WebView2 里连播 3 分钟，工作集约 500 MB 后走平，暂停/跳转/继续正常。
5. **120 秒上限**：`BGM_MAX_SECONDS = 120` 管住界面滑块、单首、批量清单和配乐服务；原 380 秒逻辑没删，以后只改这一个常量。
